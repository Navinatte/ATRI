# ATRI-bot 官网 · 视觉与交互设计规范

> 版本 **v0.19（草稿·进行中）** · 起草 2026-09-17 · 修订 2026-09-19 · 状态：**待评审**
>
> **修订记录**
> - **v0.19** —— **文档内部转场返工：无离场 + 只淡正文（§6.14）。**
>   用户原话：「文档内部页面的切换不是右上角那一行按键点击后不同页面的切换，
>   所以不需要这个翻页的感觉」。
>   ① **离场不再做梦任何事** —— 点击处理器里文档内部链接直接 `return`，
>   不 `preventDefault`、不写 `data-nav-out`。v0.18 只改了到达，
>   离场仍按 `ORDER` 算出 `forward` 播 `navPushOutLeft`，用户一眼就看出还是翻页。
>   ② **淡化收到 `.docs__article` 这一层**，不再淡 `.docs` 整块 ——
>   侧边栏两页完全一样，是视觉锚点，淡它就像换了页。
>   VT 路径相应改用 `view-transition-name:doc-article` 命名组，
>   root 那一路在 `fade` 下不带任何动画（v0.18 是挂在 root 上，错）。
>   ③ 跨栏目平移不受影响，六组实测见 §6.14。
>   ④ 记一条**工具教训**：量「到达瞬间」的动画不能靠 `waitForNavigation`，
>   也不能在一次 `evaluate` 里轮询 URL —— 导航会销毁执行上下文。
>   改用 CDP `Page.addScriptToEvaluateOnNewDocument` 让到达页自己采样。
>   ⑤ **修掉生成器的标题 bug。** `render()` 里写成 `lvl = kind[1]`，
>   `kind=='h2'` 只取到第二个字符 `'2'` ⇒ 输出 `<2 id="intro">前言</2>`。
>   非法标签名（数字开头）不会报错，解析器整串当**文本**渲染，
>   于是正文里印出 `</2 id="intro">`。侧边栏锚点用的是完整的 `'h2'`，
>   所以只有正文坏 —— 它看起来像样式问题，其实是字符串 bug。
>   生成器新增自检④：扫所有标签名，非字母开头即报错（放行 `!` / `?`，
>   那是 `<!DOCTYPE>` 与注释）。**新增自检要拿坏样本喂一次**，
>   否则区分不了「真没问题」和「检查写坏了」。
>   ⑥ **正文里的「官网：亚托莉.top」删掉。** 文档页本身就挂在这个域名下，
>   正文再指一遍是自己指自己，域名一换还得回来改内容。
>   （仓库 Issue / LICENSE 两条外链保留 —— 仓库不是官网。）
>   ⑦ **顶部留白收窄。** 用户反馈「上方的空白区域有点大」。
>   原来照抄落地页的 168px，而导航只占 72px ⇒ 中间空了 96px。
>   文档页改为 **120px**（≤ 899px 时 110px），桌面净空 48px。
>   ⑧ **宝箱的「下载」改走 `fetch` → Blob → object URL（§6.13）。**
>   用户反馈「点击后不应该跳出一个音频界面」。
>   根因是 `download` 属性**只对同源资源生效** —— 不同源时浏览器**静默忽略**它，
>   直接导航过去。而「同源」不由页面控制（反向代理 / 内嵌 WebView / 域名重写
>   都可能把资源变跨源）。改成 `blob:` URL 就恒同源了。
>   ❗坦陈一句：**本地没能重现这个症状**（实测链接触发时既不导航也不报错），
>   所以这一改是「拔掉对运行环境的依赖」，不是「修掉一个已重现的 bug」。

## 2. 设计理念

### 2.1 一句话

> **把网站做成"深夜的海面"——大面积沉默的深蓝，和一点点随时会熄灭的暖光。**

参考图里，花火是唯一的暖源；整个画面把光借给那一小簇火，其余全部归还给夜色。网站照这个比例分配视觉资源。

### 2.2 三条不可违背的原理

**① 光守恒律（Warmth Budget）**
暖色像素占比目标 **6% ~ 10%**，绝不越过 12%。任何新增元素默认用冷色；只有被明确判定为"这里需要一点温度"时才发放暖色配额。

> **v0.7 限定：这条律只管夜间。** 它描述的是"夜里的海靠少数几点光"这件事 —— 稀疏、点状、高彩度（§3.8.3 的暖色机制）。
>
> 晨昏不适用这条，因为它们用的是**另一个机制**：太阳贴着地平线时，大气把它拉成一条**低彩度、高颜面积的色带**，靠的是"多而淡"。若拿 12% 去卡晨昏，得到的会是"地平线上一小块橙斑"—— 那不是日出，那是只有一盏路灯的夜。
>
> 所以完整规则是：**夜间的暖色靠配额（点光源），晨昏的暖色靠位置（只准出现在 `skyHorizon` `glow` `light` `seaNear` 四层，天顶必须保持冷色）。**

**② 双声部制（Two Voices）**
参考图里同时存在两种画法，它们**永不混用**：

| | 少女声部 | 吉祥物声部 |
|---|---|---|
| 对应素材 | `atri.png` / 夜海 | `ATRI-bot.png` |
| 载体 | 全部正文、导航、卡片、表格 | 加载 / 空状态 / 错误 / 彩蛋 / Logo |
| 形状 | 硬边矩形、1px 发丝线、V 形切角 | 圆钝胶囊、粗描线、贴纸感 |

> **v0.3 注**：全站已改为单一字族（§3.2），因此**字族不再是声部的区分手段**。上述六个维度中，形状与色彩承担主要区分职责，"不要把胶囊形和粗描线带进功能卡片"这条纪律变得比以前更重要。详见 §3.2.8。

**③ 形状各有其主**

| 形状 | 出处 | 允许出现的位置 |

#### 3.2.3 为什么是圆体——一次被删掉的方案

v0.1 的主张是「标题用宋体表达哀感」。v0.2 改为圆体，理由如下：

**① 圆体的骨架是黑体，所以它担得起正文**
江城圆体源自思源黑体，字面方正、重心稳定、笔画粗细均匀——它是「装饰后的黑体」，不是手写体。这保证了信息传达的清晰度。而宋体在深色底 + 小字号下的横画会发虚，反而损害可读性。

**② 圆体与三张素材是同一个形状家族**
回看 §1 的取色与素材：Q 版 Logo 是**圆钝轮廓 + 粗描线**，水手服的领口是**弧线**，花火的光晕是**圆形**。圆体的笔画末端收圆，正好接住这三者。宋体是尖角，在这套素材里是唯一的外来者。

**③ 圆体同时具备「精度」与「柔软」**
思源黑体的骨架给了它精度（这是亚托莉的「高性能」面），圆润的笔端给了它柔软（这是她的「少女」面）。一个字族能同时承载这两面，比用两个字族去拼接更统一。

**④ 与项目母本的基调一致**
这个故事的底色是温暖的、日常的、带着一点哀感的夏日；不是冷峻的科幻。圆体读起来是「有人陪着你」，宋体读起来是「一段被记载的历史」。

> **代价**：删掉方圆对比之后，首屏标题的视觉张力靠**字重反差**来建立（Bold 700 对 正文 Regular 400），而不是靠字形对比。这意味着**字重纪律必须被严格执行**——见 §3.2.6。

#### 3.2.4 为什么最终不用阿里妈妈方圆体（决策记录）

方圆体在视觉上其实很合适——它有一条 `BEVL` 轴，可在「方（仿生人）」与「圆（少女）」之间连续调节，正好对上亚托莉的双重性。放弃它是因为许可：

| | 江城圆体 | 阿里妈妈方圆体 |
|---|---|---|
| 许可 | **SIL OFL 1.1** | **「作者声明」** |
| 版权人 | 刘鹏 | **淘宝（中国）软件有限公司** |
| 免费商用 | ✅ | ✅ |
| **可修改 / 子集化 / 转格式** | ✅ **明文允许** | ❌ **明文禁止**「新增、拆分、修改或以其他方式进行二次创作」 |
| 用于商标 | ✅ | ❌ 禁止 |
| 署名 | 不要求 | **必须标注版权人** |

**「作者声明」禁止对字体做拆分与修改，而把 TTF 转成 WOFF2 子集恰好落在这一条上。** 规避方式只有两种：一是把标题导出为 SVG 路径（不涉及字体文件分发），二是全站改用江城圆体。

选择了后者，因为它把架构从「两套字体 + 两种交付方式」压缩成「一套字体 + 一种交付方式」，也让首屏无需为了一个标题额外加载任何东西。这个是*简化*，不是牺牲。

> 若日后想把方圆体加回来，唯一安全的用法是：**只用于图形化的标题**（导出 SVG `<path>` 或 PNG，不随站点分发字体文件），并在页脚署名 `阿里妈妈方圆体 © 淘宝（中国）软件有限公司`。

```css

@font-face{

  /* 主字体：江城圆体 → 思源黑体 → 系统黑体 */
  --font-display:"JiangCheng Yuan",var(--font-cjk);
  --font-sans:var(--font-display);

  /* 日文：零下载 */
  --font-jp:"Yu Mincho","Hiragino Mincho ProN","Source Han Serif JP",
            "Noto Serif JP",serif;

  /* 等宽：末尾必须追一个中文黑体，否则 mono 里的中文会回退成宋体 */
  --font-mono:ui-monospace,"JetBrains Mono","Cascadia Mono",Consolas,
              "SFMono-Regular","Noto Sans Mono",monospace,var(--font-cjk);

```

**降级策略**：`--font-display` 末端永远挂着系统黑体栈。字体加载失败时页面仍然完整可读，只是观感变普通——不会有「豆腐块」，也不会有布局跳动（已在 §3.3 约束了行高，两种字体的行高差异被吸收）。

**日文为什么不用江城圆体**：它确实含假名，但那套假名是繁体中文语境下的字形，用来排「時よ止まれ、おまえは美しい」会不对味。这句是**诗**，该用衬线（明朝体）——衬线的抑扬起伏，正是「时间流逝吧，你是多么的残酷」的语气。而且系统明朝体零下载。

**子集化（OFL 允许，且强烈建议）**

完整的 21,632 字单字重约 5~8 MB。本站实际用字估计在 800~1500 字之间，子集化后单字重可压到 **约 100~180 KB**（WOFF2）。

```bash
# 用 fonttools（pip install fonttools brotli）
# --text-file 传入「全站实际用到的所有字符」去重后的 txt
pyftsubset JiangChengYuanTi-Regular.ttf \
  --text-file=chars.txt \
  --flavor=woff2 \
  --layout-features='*' \
  --output-file=jiangcheng-400.woff2
```

> **必须保留**：标点（`，。；：（）「」、！？——…`）、数字、英文字母、全角空格、`©` `·` `→` `↔` `✓` 等符号。
> **改文案后必须重新子集化**，否则新增的字会静默回退成系统字体。**建议把这条写进构建说明。**

#### 3.2.6 字重经济与禁用项

江城圆体有 6 个字重，但**每多一个字重就多约 150 KB**。本规范的取舍：

| 字重 | 用 | 说明 |
|---|---|---|
| **400** | ✅ **必需** | 正文、表格、说明——80% 的文字 |
| **700** | ✅ **必需** | 所有标题、导航、按钮。删掉方圆对比后，**它是全站唯一的视觉重音** |
| 300 | ⬜ 可选 | 仅吉祥物台词。首版用「400 + `--mascot-flax` 颜色」代替 |
| 500 | ❌ 不用 | 与 400/700 的差异在本站尺度下看不出来，不值得那 150 KB。**v0.3 起不再使用** |
| 600 / 900 | ❌ 不用 | 同上 |

**首版只加载 400 + 700 两个字重（约 300 KB）。** 页面里出现的任何 `font-weight: 500` 都是错误——它会被浏览器在 400 与 700 之间合成，在中文笔画密集的字形上容易发糊。

**字重纪律（因为只剩两个字重，这条变得关键）**

| 元素 | 字重 |
|---|---|
| 首屏大标题 | 700 |
| 区块标题 `--fs-h1` / `--fs-h2` | 700 |
| 卡片标题 / 功能条目标题 `--fs-h3` | 700 ⬅ **v0.3 起从 500 升为 700** |
| 导航项 | 700 |
| 按钮文字 | 700 |
| 正文 / 描述 / 表格 | 400 |
| 等宽标签 `--fs-label` | 400 |
| 吉祥物台词 | 400（或 300） |

> **禁止**用 `font-weight: 100~200` 或 `800~900`——江城圆体在这两端要么没有对应字重（触发合成），要么会显得笨重，破坏「克制的哀感」。

#### 3.2.7 已知问题与规避

| 问题 | 规避 |
|---|---|
| 作者本人声明：**「不建议用于文章正文，正文还是乖乖用思源黑体」**（起因是行高与部分标点宽度） | 正文行长已压到 34em、行高 1.90（§3.3）；上线后按实际观感决定是否把正文单独切回系统黑体 |

| 顿号、句号等标点宽度曾偏窄 | 用 `letter-spacing` 微调，或在子集化时确认标点已被包含 |
| 部分软件中字重全显示为 `Regular`（style 字段未区分） | 只影响桌面设计软件；浏览器按 `font-weight` 描述符正确选择，不受影响 |
| 字体名在中英文系统下不一致 | 引用时以 `@font-face` 的自定义名 `JiangCheng Yuan` 为准，不依赖系统名 |

#### 3.2.8 双声部靠什么区分（受本次变更影响的规范）

§2.2 的双声部制原本隐含「靠字族区分」。现在只有一个字族，**双声部的差异改由以下四项共同承担**：

| 维度 | 少女声部 | 吉祥物声部 |
|---|---|---|
| 字重 | 700 / 400 | 400（或 300） |
| 颜色 | `--fg`（暖白）/ `--fg-muted` | `--mascot-flax`（亚麻） |
| 形状 | 硬边矩形、1px 发丝线、V 形切角 | 圆钝轮廓、1.5px 描线、胶囊 |
| 尺度 | 大（`--fs-h1` 起） | 小（`13~14px` 台词） |

**字族不再是区分手段**，因此「不要在功能卡片里用胶囊形」这类形状纪律变得比以前更重要。

### 3.8 昼与夜：一条色相轴，两种极性（+ 晨昏暖色）

> **⚑ 本期上线范围（v0.8 决定）：正式站只做「白天 / 夜晚」两套静态色值，不接时间轴。**

> 一天里呈现的是两次明显的"变色事件"，而不是想象中的流动。与其带着一个半成品上线，
> 不如先只取两个端点；时间轴改为后续迭代。
>
> 这意味着实施时：
> - `data-polarity` 仍保留，但只取 `night` / `day` 两个值，**时间轴上的一切都不写**
> - §3.8.3.1（晨昏锚点）§3.8.4（死区与遮罩）§3.8.5（插值）§3.8.7（更新策略）**本期不实现**
> - 但**它们全部保留在规范里** —— 是已验证的成果，第二期直接接上即可，不用重新推算
> - §3.8.3 的两个实测锚点仍是最重要的资产：**两套极性的令牌值就取自那里**
>
> 具体怎么落地见 **§3.9**。

v0.1 的色彩只描述了夜晚的海。本节把它扩展成一条 24 小时连续演进的曲线，站点**默认跟随访客的本地时间**。除了两个实测锚点（夜 / 昼），v0.7 又补了四个**推导**的晨昏暖色锚点 —— 于是现在清晨与傍晚是真的有橘子色的。

> **本节为 v0.5 重写，v0.6 / v0.7 两轮修正。** 旧方案（v0.4）的色盘已废弃，理由见 §3.8.1；本节保留了旧稿中已被验证有价值的部分：插值例外（§3.8.5）、令牌跟随范围与更新策略（§3.8.7）、shader 设计要点（§3.8.8）、降级清单（§3.8.9）。

> **读这一节时请记住它内部的依赖顺序：** §3.8.3 定锚点 → §3.8.3.1 推晨昏 → §3.8.4 算死区与遮罩 → §3.8.6 查对比度。后面每一个结论都只依赖**相对亮度**，所以只要新加的颜色不改变亮度，就不用重跑前面三节。

#### 3.8.1 核心原理：同一根轴，两种极性，外加晨昏两个暖锚点

旧方案（v0.4）把色盘拆成「底色层 / 光层」，规定底色层**永远压暗**以满足白字对比度，并据此宣称"本系统不产生浅色主题"。这条路**经实测证明走不通**：

- `enforce()` 是靠**线性调暗**满足 5:1 的，于是正午变成 `skyTop #082a4a` / `seaFar #0d6795` —— **仍是深海军蓝**
- 只有细条带状的 `glow` 是亮的，而底色层占画面约 90%，所以整页仍读作夜晚
- **根因**：参考图 `ATRI-bot-day.png` 是**高调**的（66% 像素亮度 > 0.35，见 §1.3），而"白字 + 每层底色都达 5:1"**在数学上禁止高调背景**

所以不是调色不好，而是**约束错了**。正确的做法是：

> **白天不是"亮一点的夜晚"，而是把极性翻过来 —— 浅底 + 深字。**

而翻过来之后，两个主题并不需要两套配色，因为实测发现：它们**本来就是同一根色相轴上的两个位置**。

| 配对 | 夜晚 | 白天 | 色相差 |
|---|---|---|---|
| 海面 | `#2664ab` H=254.3 | `#1878d8` H=253.6 | **−0.6°** |
| 海面·受光 | `#5a8dc3` H=250.9 | `#4a9deb` H=249.4 | −1.5° |
| 地平线 | `#223a68` H=262.2 | `#b7defc` H=241.4 | −20.7° |
| 页面底 | `#142f5c` H=260.0 | `#d3eafd` H=243.5 | −16.5° |

海面那一对的色相差只有 **0.6°** —— 它们在色相环上几乎是同一个点。所以：

**昼与夜是两个明度位置，不是两套颜色。** 这才使得"连续插值"技术上成立（§3.8.4 会说明插值真正的障碍在哪里）。

#### 3.8.2 极性：令牌语义如何反转

极性反转的是**语义层**（§3.1），不是原始色阶。这正是 §3.1 强制"组件只准用语义层"的回报：切换主题时组件代码一行不改。

| 语义令牌 | 夜晚（深底浅字） | 白天（浅底深字） |
|---|---|---|
| `--bg-base` 页面底 | `#0a1223` | `#d3eafd` |
| `--bg-panel` 面板 | `rgba(20,47,92,.62)` | `rgba(255,255,255,.62)` |
| `--bg-code` 代码块 | `#070d18` | `#0b2c47` ⬅ **仍是深色**（见下） |
| `--fg` 正文 | `#fcfaf3` | `#0e3557` |
| `--fg-muted` | `rgba(252,250,243,.68)` | `#24486b` |
| `--fg-faint` 仅装饰 | `rgba(252,250,243,.60)` | `#25455a`（**v0.6 修过一次，v0.13 又修了昼值，见 §3.8.6**）|
| `--accent` | `#70b5d5` | `#0b4a7d` |
| `--line-color` | `rgba(252,250,243,.14)` | `rgba(14,53,87,.16)` |
| `--accent-warm` | `#fbe4cf`（琥珀） | `#7a4712`（推导，见 §3.8.3）|
| `--scrim-color` | `#142f5c` | `#d3eafd` |

> `--scrim-color` 是 §3.8.4 那层整页遮罩的颜色，它**必须与实现里参与对比度反解的常数逐字符一致**。夜取 `#142f5c`（恰好是 `--bg-panel` 的基色，于是面板会无缝融进雾里），昼取页面底色 `#d3eafd`。

**两个不反转的例外**：

1. **`--bg-code` 永远是深色**。白天它是深海 navy `#0b2c47` + 暖白字（对比度约 13:1）。这是故意的：代码块是"海的一小块"，也避开了浅色主题里代码不好看的老问题。
2. **`--ribbon-500` 红永远是同一个红**。它是品牌识别锚点，两套主题共用。

#### 3.8.2.1 光层不参与极性反转

极性翻转的是**底色与文字**。**光层不参与翻转** —— 它始终是"亮的东西"，只是颜色的冷暖与强度随时间变。

| | 夜晚 | 白天 |
|---|---|---|
| 光层是什么 | 线香花火（暖） | 太阳眩光（**冷白**）|
| 色值 | `#fbe4cf`（实测） | `#edeffc`（实测） |
| 呈现方式 | 局部光斑 / 花火 | 局部光晕 + **水面色带** |

> 一句话：**极性管"底和字"，光层管"现在几点"。** 底色可以整片翻转，光层只换颜色。

#### 3.8.3.1 晨昏：推导锚点（**只改色相，不提亮**）

夜与昼是两个实测锚点，但一天里色相变化最剧烈的恰恰是中间那两段。晨昏必须有暖色 —— 真实世界里太阳贴着海面，光走的路径最长，天顶还是冷的，地平线已经烧起来了。这是一条必须满足的观感要求，不是装饰。

问题在于：一旦开始"凭感觉调暖色"，就等于回到 v0.4 的老路。所以这里给一个**可验证的推导规则**：

> **规则：晨昏锚点的每一层，其 `OKLCH L` 直接继承「夜 ↔ 昼」基线曲线在该时刻的取值。只换色相（H）与彩度（C）。**

为什么这条规则有效：**OKLab 的 L 就是感知明度**，同 L 换色相几乎不改变相对亮度。而 §3.8.4 与 §3.8.6 的全部结论（死区位置、遮罩厚度、四枚令牌的下限）都只依赖**相对亮度**。于是"加暖色"这件事在数学上就不会动到任何一条已验过的可读性保证。

**实测对照**（`temp/verify_dawn.py`，5 层底 × 辉光叠加 × 4 枚令牌 × 每半小时扫 24 小时）：

| | 插入晨昏锚点前 | 插入晨昏锚点后 |
|---|---|---|
| 失格处数 | 0 | **0** |
| 遮罩厚度峰值 | 0.828 | **0.828** |
| 厚度曲线 | 05:30 `0.36` / 06:00 `0.62` / 06:30 `0.83` / 07:00 `0.25` … | **逐字相同** |

两边**逐字相同**。这就是这条规则值钱的地方：暖色是白拿的。

**四个锚点**（★ = 推导）：

| 时刻 | 名称 | `skyTop` | `skyMid` | `skyHorizon` | `glow` | `light` | `star` |
|---|---|---|---|---|---|---|---|
| 05:45 | ★ 拂晓 | `#242c4d` | `#44375a` | `#9b3801` | `#a95601` | `#ffe4cf` | .18 |
| 06:30 | ★ 日出 | `#737ea4` | `#9588af` | `#f37f50` | `#fb964b` | `#ffe9d7` | .02 |
| 18:06 | ★ 日落 | `#657398` | `#9377a5` | `#f16a57` | `#ff7f5c` | `#fee8de` | .02 |
| 19:00 | ★ 暮色 | `#101a38` | `#381f46` | `#900700` | `#a72d01` | `#ffe3d7` | .26 |

推导时用的色相：

| 分组 | `skyTop` | `skyMid` | `skyHorizon` | `seaNear` | `seaDeep` | `glow` | `light` |
|---|---|---|---|---|---|---|---|
| 拂晓 / 日出 | 272 | 300 | **42** | 32 | 258 | **55** | 62 |
| 日落 / 暮色 | 268 | 312 | **30** | 22 | 256 | **36** | 44 |

**三条设计决定**：

1. **暖色集中在地平线。** 只有 `skyHorizon` `glow` `light`（以及反出暖色的 `seaNear`）转暖，天顶反而偏紫（H≈272 的紫罗兰 / H≈312 的梅紫）。所以是"地平线暖、天顶冷"，而不是整屏橘子色。
2. **清晨偏金黄，傍晚偏橘红。** 晨光 H=55（`#fb964b`）、暮色 H=36（`#a72d01`）—— 一个正在亮起来，一个正在熄下去。两者不会看混。
3. **海面接住暖色。** `seaNear` 在日落时是 `#b97673`（暖粉倒影）、拂晓时是 `#733f35`（暖褐），是整幅画面里最像"水"的一处。

**剩下的局限（唯一一条）：色相仍属推导，不是实测。** 明度有实测锚点背书、可读性有脚本背书，但"夕阳到底更橙还是更红"没有参考图可对。一旦补上日出/日落的海景图，应当比照替换这四个锚点的 H/C（**L 不要改**）。只需多两个锚点，插值逻辑不动。

#### 3.8.4 死区与遮罩交接

这是整套系统最关键的技术点。背景从深连续插值到浅，中途会穿过一段**白字与深字都不达标**的亮度带。

##### 死区在哪

背景从深插值到浅，中途会穿过一段**白字与深字都不达标**的亮度带。实测定位：

| 背景 OKLCH L | 白字 `#fcfaf3` | 深字 `#0e3557` | 结论 |
|---|---|---|---|
| 0.44 | 7.41 ✓ | 1.63 | 夜晚极性可用 |
| 0.52 | 5.26 ✓ | 2.30 | 夜晚极性可用 |
| **0.56** | **4.44 ✗** | 2.72 | **死区开始** |
| 0.62 | 3.77 | 3.20 | 死区 |
| 0.68 | 2.75 | 4.39 | 死区 |
| **0.72** | 2.37 | **5.10 ✓** | **死区结束** |

**死区 = OKLCH L 0.558 ~ 0.686**（对应相对亮度 0.174 ~ 0.324）。跨过去大约需要 1~1.5 小时。

##### 解法：整页遮罩，厚度反解（Scrim Handover）

> **规则：文字永不直接坐在环境底上跨过死区。**

**先纠正一个容易走偏的地方：遮罩必须是"整页"的，不能只做"面板"的。**

v0.6 曾把遮罩实现成"把面板的不透明度顶到 1"。那是错的，而且错得很隐蔽：面板只能保护**落在面板里的**文字，而页面上有大量文字直接坐在海面上 —— `.sec__desc` 的 `--fg-muted`、`.sec__tag` 的 `--accent`、色卡里的十六进制值……这些文字在死区里完全裸奔。用严格判据（5 层底 × 辉光叠加 × 4 枚令牌 × 每半小时）量过：**v0.6 的实现有 59 处失格**，而教科书式的"换个角度看看"是看不出来的。

所以遮罩的层级是：**环境层 → 地平线辉光 → 整页遮罩 → 全部内容**。`--t-scrim-a` 为 0 时它完全不可见，等于不存在。

**第二步：厚度的来源。**

遮罩厚度**不写死常数**。每帧从"当前极性的四枚令牌必须在文字可能踩到的每一个底上都 ≥ 4.5:1"这个约束里**反解**出最小厚度：

```
若 最差对比度(alpha = 0) ≥ 4.5        →  alpha = 0        （常态，完全不遮）
否则 二分 20 次求最小 alpha ∈ [0,1] 使 最差对比度(alpha) ≥ 4.5
```

于是它自动获得三个性质：**该为零的时候就是零**（一天里大约 85% 的时间遮罩完全不存在）；**需要多厚就多厚**（不需要为某一天的极端情形预留常数）；**加了暖色也不会误触发**（§3.8.3.1 已验证插入晨昏锚点前后厚度曲线逐字相同）。

算的时候层级顺序不能弄错 —— 必须是"环境层 → 辉光 → 遮罩"，把遮罩写在辉光下面会把辉光的亮度重复计一次，从而高估所需厚度。

**第三步：翻转时刻与遮罩颜色。**

1. **翻转时刻 = 两条对比度曲线的交点。** 白字曲线 `(0.955+0.05)/(Y+0.05)` 与深字曲线 `(Y+0.05)/(0.0324+0.05)` 相等时 `Y = 0.2378`，即 **L = 0.6195**。那一刻两种极性一样差，换过去最不突兀。按 §3.8.3 的锚点位置解出：**06:41** 转白天、**17:46** 转夜晚。
2. **遮罩颜色 = 当前极性的页面底色**（夜 `#142f5c`，昼 `#d3eafd`）。取底色而不是纯白，是为了让交接看起来像**起雾**，而不是**闪一下白光**。它恰好等于 `--bg-panel` 的基色，所以面板会无缝融进雾里。
3. 遮罩颜色与整个极性组在**同一次样式写入**里换掉 —— 跨帧就会闪。环境层不受影响，继续连续插值。

> **`--scrim-color` 必须与 JS 里的 `SCRIM_COLOR` 逐字符一致。** 它是参与对比度反解的常数，不是"写着好看的那个色"。演示页里这条注释就写在这个令牌旁边。

##### 实测数字

**死区定位**（背景 OKLCH L ↔ 两套文字）：

| 背景 OKLCH L | 白字 `#fcfaf3` | 深字 `#0e3557` | 结论 |
|---|---|---|---|
| 0.44 | 7.41 ✓ | 1.63 | 夜晚极性可用 |
| 0.52 | 5.26 ✓ | 2.30 | 夜晚极性可用 |
| **0.56** | **4.44 ✗** | 2.72 | **死区开始** |
| 0.62 | 3.77 | 3.20 | 死区 |
| 0.68 | 2.75 | 4.39 | 死区 |
| **0.72** | 2.37 | **5.10 ✓** | **死区结束** |

**死区 = OKLCH L 0.5576 ~ 0.6846**（对应相对亮度 0.174 ~ 0.324）。

**遮罩厚度**（`temp/verify_dawn.py`，每半小时扫 24 小时）：

| 指标 | 数值 |
|---|---|
| 峰值 | **0.828**（出现在 06:30 与 18:00 附近） |
| 非零时段 | 一天 48 个采样点里占 **8 个**，约 3.5 小时 |
| 时段曲线 | 05:30 `0.36` / 06:00 `0.62` / 06:30 `0.83` / 07:00 `0.25` ／ 17:30 `0.25` / 18:00 `0.80` / 18:30 `0.67` / 19:00 `0.17` |
| 失格处数 | **0** |

**驱动遮罩厚度的是 `--accent`，不是正文。** 峰值时刻（06:30）若不加遮罩，四枚令牌的最差对比度是：

| 令牌 | 最差 | 说明 |
|---|---|---|
| `--accent` `#70b5d5` | **1.07** | 罪魁 |
| `--fg-faint` | 1.67 | |
| `--fg-muted` | 1.78 | |
| `--fg` `#fcfaf3` | 2.33 | 正文反而是最好的 |

原因是**青色强调与中间调的底几乎没有亮度差**。把这条推导出来会得到一个更硬的结论：在 L=0.598 的底上要达到 4.5:1，文字亮度必须 ≤ 相对亮度 0.0087（约 L 0.21）—— 那已经是"近黑"，而它在夜间的深底上又必然失格。**同一枚 `--accent` 无法同时服务深底与中间调底**，所以这里只能靠整页遮罩，不能靠换强调色。

**结论：整页遮罩是唯一解，不是权宜之计。**

> **不要靠"给文字加粗/加阴影"来抢救对比度。** 那是掩盖问题 —— 正确做法是换极性，或者在交接窗口里把遮罩加厚。

**代价要说清楚**：峰值 0.83 意味着一天中有十几分钟，整页会近乎变成一片平的底色，晨昏的暖色被压得很淡。这是刻意的取舍 —— 宁可那一小段时间像"起雾"，也不让文字读不成。**如果哪天想把这个代价压下去，唯一的方向是减少直接压在裸环境底上的文字**（比如让 `.sec__tag` `.sec__desc` 也进面板），而不是把遮罩调薄。

#### 3.8.5 插值：OKLCH 与近中性色例外

**必须用 OKLCH 而不是 sRGB。** 在 sRGB 里插值会让两个不同色相的中间点掉进灰泥；OKLCH 的 L/C/H 分离保证了色相旋转时明度与彩度各自可控。

但**纯 OKLCH 极坐标插值有一个坑，实现时必须绕开**：

> 当两端的彩度都很低时，**色相是没有意义的**（一块近灰色谈不上"什么颜色"），可极坐标仍会老老实实按角度旋转，于是旋转路径会穿过真实存在的绿色或黄色。
>
> **实测**：正午地平线 `#eaf6fa`（H=220，C=0.014）→ 下午 `#eadcc6`（H=79，C=0.033），
> 极坐标插值在 t=0.5 处得到 **`#deede0` —— 一片苍绿**。矩形插值得到 `#eae9e0`（干净的中性色）。

**规则**：

```
若 min(C₁, C₂) < 0.05   →  在 OKLab 直角坐标插值（保留 a/b 分量线性混合）
否则                     →  在 OKLCH 极坐标插值（色相走最短弧）
```

这条规则同时解释了一个现象：真实天空从蓝转橙时**中间必然经过一段近白**（彩度塌陷）。这不是缺陷，是它看上去自然的原因。

**缓动**：锚点之间的 `t` 用 `smoothstep`（`t²(3-2t)`），避免在锚点处出现速度突变。

#### 3.8.6 对比度保障（两套下限）

极性反转后，对比度不再是"白字 ≥ 5:1"一条规则，而是**两套**：

| 极性 | 主体文字 | 下限 | 实测最差 |
|---|---|---|---|
| 夜晚（深底浅字）| `--fg #fcfaf3` | ≥ 4.5:1 | **5.76**（在 `--sea-500` 上）|
| 白天（浅底深字）| `--fg #0e3557` | ≥ 4.5:1 | **7.65**（在 `#96d0fd` 上）|

两套的次一级文字：

| 极性 | `--fg-muted` | 最差 | `--fg-faint` | 最差 | 结论 |
|---|---|---|---|---|---|
| 夜晚 | `rgba(252,250,243,.68)` | 7.80 | `rgba(252,250,243,.60)` | **5.40** | ✓ |
| 白天 | `#24486b` | 5.75 | `#25455a` | **5.28** | ✓ |

> ❗**`--fg-faint` 的下限方向，两个极性是相反的 —— v0.13 才改对。**
>
> “下限按环境底的最浅处定”这句话**只对夜晚成立**。夜晚是浅字压深底，
> 底越亮字越难认，所以最差在**最亮**处。
> 白天是深字压浅底，底越暗字越难认，所以最差在**最暗**处 ——
> 而白天页面最暗的地方不是天空，是**底部暗角**（`--vig-b` 压出来的 L≈0.53）。
>
> 按最亮处（天顶 `#96d0fd`，L=0.587）算，旧值 `#35566b` 确实有 4.73；
> 但按最暗处（L≈0.529）复算只有 **4.29** —— 实测确认，**改造前就已失格**。
> 同色相/彩度下调 L（0.437 → 0.376）得 `#25455a`，最差点上也达 5.57:1。
>
> **教训**：写“最差在环境底的某个极值处”时，先把极值标清楚 ——
> 这里只说了“最浅处”，而白天的极值其实是“最深处”。

> **`--fg-faint` 只准用于装饰性文字。** 它踩在 `--panel--hero` 那种更亮的渐变面板上时还会更差，
> 所以规则是：**任何需要被读到的值（十六进制、坐标、标签）一律用 `--fg-muted`。**
>
> v0.6 补过一次（v0.5 的 `.44` / `#5c7f9b` 在环境底上只有 **4.22 / 2.27**）。

**两条不可使用的背景**（实测）：

- 夜晚：`--sea-500 #2664ab` —— 任何白字系文字在这里都不达标（最优 5.76 已接近底线，而 `--fg-muted` 只有 3.55）
- 白天：天顶 `#48a6fb` —— `--accent` 在这里只有 4.93、`--fg-muted` 4.60，余量太紧。它只能出现在**装饰**里

> **不要靠"把文字加粗/加阴影"来抢救对比度**。那是掩盖问题。正确做法是让每层的取值待在安全带内。

#### 3.8.7 令牌跟随范围与更新策略

**只有环境层与光层跟随时间（连续插值）；极性组不插值，而是阶跃。** 其余令牌冻结，避免整站不可预测地漂移：

| 令牌 | 随时间 | 理由 |
|---|---|---|
| `--t-sky-top` `--t-sky-mid` `--t-sky-horizon` `--t-sea-near` `--t-sea-deep` `--t-glow` `--t-light` `--t-star` `--t-glow-a` | ✅ **插值** | 环境层与光层本体 |
| `--t-scrim-a` | ✅ **反解** | 每帧解出刚好够用的厚度（§3.8.4），不是插值也不是常数 |
| **整个极性组**（§3.8.2 那张表：`--bg-base` `--bg-panel` `--fg` 系 `--accent` 系 `--line-color` 系 `--scrim-color`）| ⛔ **阶跃** | 插值就会穿过死区 —— 这是全篇最硬的一条 |
| `--accent-warm` | ⛔ 在极性组里 | 夜 `#fbe4cf` / 昼 `#7a4712` —— **不再等于 `--t-light`** |
| `--ribbon-500` `--bg-code` 的"永远深底"性质 | ❌ 冻结 | 品牌识别锚点；代码块永远是深色 |

> 星点（`--t-star`）属于环境层，所以它随晨昏淡出：夜里 `.55` → 拂晓 `.18` → 日出 `.02` → 白天 `0`，傍晚再渐亮到 `暮色 .26`。

**更新策略**：JS 每 **20 秒** 重算一次并写入 CSS 变量；用 `@property` 把变量注册为 `<color>`，于是**变化本身由 CSS 过渡在 20 秒内平滑完成**。

这样做的收益：
- 不需要 rAF 循环，**空闲时零帧开销**
- 20 秒内的色差肉眼不可辨，观感上就是连续流动
- 即使浏览器不支持 `@property`（降级为瞬时切换），20 秒的步进幅度也小到看不出跳变

```css
@property --t-sky-top { syntax:'<color>'; inherits:true; initial-value:#070d18; }
@property --t-scrim-a { syntax:'<number>'; inherits:true; initial-value:0; }
/* …其余同理 */
:root{ transition: --t-sky-top 20s linear, --t-scrim-a 20s linear /* … */; }
```

**成本提醒**：每次重算要反解一次遮罩厚度（约 20 次二分 × 20 次对比度计算）。这在数量级上可以忽略，但**滑块拖动时是逐帧触发**的 —— 所以拖动路径上必须加 `transition:none`（演示页用 `html.tt-off` 类实现），否则厚度会滞后于拖动手感。

#### 3.8.8 海面 shader（**暂缓至第二期**）

CSS 渐变能表达"一天的颜色"，但表达不了**光在水上的样子**。而参考图真正的灵魂恰恰是那一小簇光 —— 白天它是**日照粼光带**，夜里是花火与月光。这是纯 CSS 做不到的部分，所以这里用了 shader。

**它做什么**（单个全屏片段着色器，无几何体、无纹理、无 framebuffer）

| 效果 | 说明 |
|---|---|
| 天空渐变 | 由 `skyHorizon → skyMid → skyTop` 三段混合 |
| 海面透视 | 以地平线为原点做 `1/depth` 压缩，远处密、近处疏 |
| **日照粼光带** | 光轮 x 位置下方的一条纵向光带，用两层值噪声相乘后取幂，随时间缓慢下移 |
| 地平线辉光 | 沿地平线的横带，在光轮附近最强，用 `glow` 着色 |
| 水面波纹 | 低频噪声扰动，近处振幅大 |
| 暗角 | 轻微压暗四角，让内容区更安静 |

**光轮位置跟随时间**：`x` 按 6:00(东/左) → 18:00(西/右) 移动，`y` 在正午最高、清晨傍晚贴地平线 —— 于是**白天能看到粼光带从画面左侧缓缓扫到右侧**。夜里换成月光，位置同样移动。

**关键约束：不吃性能。** 具体做法：

| 手段 | 值 |
|---|---|
| 分辨率缩放 | `min(devicePixelRatio, 1.5) × 0.7`（lite 档 ×0.45）—— 这是最有效的一项 |
| 帧率上限 | full 30fps / lite 20fps（**不是 60fps**；水的运动本来就慢） |
| 暂停 | `document.hidden` 时完全停帧 |
| 渲染精度 | `mediump`，无纹理采样，无逐帧 uniform 重建 |
| 分级 | 见下表 |
| 运行期看门狗 | 连续 60 帧平均耗时 > 22ms 自动降一档 |

**三档**

| 档 | 触发条件 | 分辨率 | 帧率 | 效果 |
|---|---|---|---|---|
| **full** | 支持 WebGL 且 ≥6 逻辑核心且非小屏 | ×0.7 | 30fps | 粼光 + 辉光 + 波纹 + 暗角 |
| **lite** | 支持 WebGL 但核心数少 / 小屏 | ×0.45 | 20fps | 仅粼光与底色，无波纹无暗角 |
| **off** | 无 WebGL / `prefers-reduced-motion` / ≤2 核心 | — | — | 退回纯 CSS 渐变 |

**性能预算**：full 档在 1080p 下约占 **1.5~3ms / 帧**（30fps ⇒ 5~9% 单核占用），GPU 侧为一个全屏 quad 的片元着色。lite 档约为其 1/4。

> **判据**：如果一个效果在 `lite` 档里不值得保留，它就不该出现在 `full` 档里 —— 因为绝大多数访客拿到的不是 `full`。

#### 3.8.9 降级与可访问性

- **`prefers-reduced-motion: reduce`** → 无时间过渡，色盘**按当前时刻静态取色**（仍然是白天/夜晚的颜色，只是不动）
- **WebGL 不可用** → 无影响（本期本就不用 shader）；第二期上线时 `.sea` 保留完整 CSS 渐变作兜底
- **`file://` 直开** → 无影响（不加载任何外部资源）
- **时间可被覆盖** → 提供 `?hour=18.5` 查询参数与调试滑块，便于评审与截图；生产环境不暴露 UI
- **不请求定位** → 只用本地时间。切换时刻是按**固定钟点锚点**建模的，不依赖经纬度
- **⏱️ 切换瞬间的闪烁**：极性是**阶跃**而非渐变，必须确保遮罩在同一次样式写入里完成切换（先升遮罩、后翻极性，不可分帧）
- **`prefers-color-scheme`**：两套主题均已存在，但**不跟随系统偏好** —— 它跟随的是时间。系统偏好只影响 `color-scheme` 元属性与表单控件外观

> **待决**：是否要为高纬度地区（夏季白夜 / 冬季极夜）提供"按当地日出日落压缩时间轴"的选项？当前方案在极端纬度下会显得与窗外不符。见 §14。

### 3.9 两套静态主题的实现（**本期实际落地的是这一节**）

§3.8 的全部推算是为了"让颜色在 24 小时里连得上"。本期只取两个端点之后，**那些约束一条都不需要了** —— 但只要不越过极性边界，就永远不会掉进死区。这是收缩范围最值钱的地方。

#### 3.9.1 极性怎么定

```js
// 白天 / 夜晚二选一，由本地时间定；用户可以手动覆盖
var day = (h >= 6.5 && h < 18);          // 06:30 ~ 18:00
var theme = localStorage.getItem('atri_theme') || (day ? 'day' : 'night');
```

| 规则 | 说明 |
|---|---|
| 默认按本地时间二选一 | 06:30–18:00 → `day`，否则 `night`。两个数字对应 §3.8.4 解出的翻转时刻区间，不要随意改 |
| 手动覆盖优先 | 用户点开关后写入 `localStorage`，此后不再跟随时间 |
| 首帧前写入 | 判断逻辑放在 `<head>` 的内联脚本里，避免"先闪一下夜晚"（FOUC） |
| 只写一个属性 | `document.documentElement.setAttribute('data-polarity', theme)` —— **其余什么都不用写** |

因为两套令牌都是纯 CSS（§3.8.2 的 `html[data-polarity="day"]`），JS 里**不需要任何颜色常量**。这与 §3.8.4 的做法正好相反：那里必须把令牌值抄进 JS 才能参与对比度反解，这里不需要。

#### 3.9.2 手动切换怎么做（复用遮罩做"过渡盖布"）

两套极性都是**已验过的安全状态**，所以理论上可以直接硬切。但硬切在 200ms 内会从深底跳到浅底，观感上像断电。做法是**把 §3.8.4 的遮罩层保留下来当过渡盖布**：

```
1. --t-scrim-a 在 180ms 内升到 1（颜色取目标极性的 --scrim-color）
2. 到达 1 的那一帧：整组极性令牌 + --scrim-color 一次写入换来
3. --t-scrim-a 在 320ms 内降回 0
```

于是切换过程是"起雾 → 换天 → 雾散"，**全程没有一帧文字压在中间调上**。这套动作已经把死区问题绕开了，代价只有一层 `position:fixed` 的纯色 div。

- 升到 1 与降回 0 可以各自用 `transition: --t-scrim-a 180ms linear` / `320ms`
- **不可跨帧**：第 2 步的极性写入必须与"遮罩到顶"发生在同一次样式写入里，否则会看到一帧糊字
- `prefers-reduced-motion: reduce` → 缩短到 `--dur-1`，行为不变

#### 3.9.3 本期不实现的部分（但已备好）

| 能力 | 状态 | 第二期接法 |
|---|---|---|
| 时间轴连续插值 | ❌ 不实现 | 把 `stateAt(h)` 接回 §3.8.5 的算法，`data-polarity` 改由它按时刻解出 |
| 晨昏四个暖色锚点（`#3.8.3.1`）| ❌ 不实现 | 直接把那张表加进 `ANCHORS` |
| 死区与遮罩厚度反解（`#3.8.4`）| ⚠️ 只保留遮罩层作过渡盖布 | 换成"每帧反解厚度"，已验证 0 失格 |
| 海面 shader（`#3.8.8`）| ❌ 不实现 | 独立 canvas，`.sea` 作兜底 |

> **保留原则**：这些代码不要删。演示页 `design/design-preview.html` 里有能跑的实现（含 OKLCH 插值、近中性色例外、厚度反解），第二期直接搬。

### 3.10 环境层：海景照片（昼夜各一张）

**动机**：纯渐变的天空/海面没有质感。换成实拍照片后，云层、地平线、月光碎浪（白天是日照粼光）都回来了，观感从一个“配色”变成一片“海”。

#### 3.10.1 图层结构

```
① .sea 的 background 第一层：遮罩（纯色，alpha = --sea-photo-scrim）
② .sea 的 background 第二层：照片（center/cover no-repeat）
③ .sea 的 background 第三层：--sea-bg 渐变    ← 兜底
④ .sea::before：上下暗角（--vig-a / --vig-b）
⑤ .sea::after ：地平线辉光（--sea-glow）
```

> ⚠️ **④⑤ 画在遮罩之上** —— 它们是 `.sea` 的**子元素**，而 `.sea` 自己的背景在它下面。
> 这不是笔误，但标定遮罩厚度时**必须**把这个顺序算进去（见 3.10.2）。

照片按极性取，靠两枚令牌切换，CSS 只有一条规则：

```css
:root{                          /* 夜 */
  --sea-photo-scrim:rgba(10,18,35,.84);
  --sea-photo:url("../img/ATRI-bot-nightsea-bg.webp");
}
html[data-polarity="day"]{
  --sea-photo-scrim:rgba(211,234,253,.88);
  --sea-photo:url("../img/ATRI-bot-daysea-bg.webp");
}

html[data-polarity] .sea{
  background:
    linear-gradient(var(--sea-photo-scrim),var(--sea-photo-scrim)),
    var(--sea-photo) center/cover no-repeat,
    var(--sea-bg);
}
```

切换昼夜时照片是**硬切**（图像层不参与 CSS 变量插值），但手动切换有 `.veil` 盖布（§3.9.2），硬切发生在盖布底下，看不见。

**降级**：照片没加载出来时只剩「遮罩 + 渐变」。已实测这条路径仍然全部达标（夜最差 6.31 / 昼最差 5.70）—— 会变平，但不会变白、也不会变得读不了。

#### 3.10.2 遮罩厚度必须实测标定

**别信解析式。** 一开始按「照片 → 暗角 → 辉光 → 遮罩」的顺序反解，夜晚得出 0.76、白天 0.80；实测分别要 **0.82** 和 **0.86+**。系统性偏差来自 3.10.1 的 ④⑤：把暗角/辉光放在遮罩**下面**，就低估了它们的影响。

标定法（`temp/calibrate_scrim.py`）：

1. 用 Playwright 把 `.sea` **单独截图**：`document.querySelectorAll('body > *')` 里除 `.sea` 外全部 `visibility:hidden`，再 `screenshot({clip})`。
2. 扫描 `--sea-photo-scrim` 的若干档（运行时 `style.setProperty` 覆盖，不必改文件）。
3. 逐像素算四枚令牌的对比度，取**全图最坏像素** —— `.sea` 是 `fixed`，滚动时照片的任意像素都可能跑到文字后面，不能只测文字当前所在那条带。
4. 同时截一张**对照组**（把 `--sea-photo` 设成 `none`，即改造前）验证测法本身可靠。

**实测结果**（下限 4.5:1）：

| 极性 | 档位 | fg | muted | faint | accent | 最小 L | 最大 L | |
|---|---|---|---|---|---|---|---|---|
| 夜 | 对照（纯渐变） | 10.16 | 5.66 | 4.78 | 4.68 | 0.0037 | 0.0490 | ✓ |
| 夜 | **0.84（现行）** | 11.32 | 6.19 | 5.21 | 5.21 | 0.0053 | 0.0388 | ✓ |
| 夜 | 照片加载失败 | 15.24 | 7.71 | 6.31 | 7.02 | 0.0048 | 0.0160 | ✓ |
| 昼 | 对照（纯渐变） | 6.95 | 5.23 | 5.57 | 5.05 | 0.5286 | 0.8224 | ✓ |
| 昼 | **0.88（现行）** | 6.58 | 4.95 | 5.28 | 4.79 | 0.4980 | 0.8469 | ✓ |
| 昼 | 照片加载失败 | 7.83 | 5.89 | 6.28 | 5.70 | 0.6023 | 0.8373 | ✓ |

> 夜晚遮罩后亮度 **0.0053~0.0388**，而纯渐变底是 0.0037~0.0490 —— 两者同一条带。
> 所以观感是「同样的夜，多了一层质感」，而不是「换了张亮图」。白天同理：
> 0.4980~0.8469 对 0.5286~0.8224，振幅甚至**变大**了（照片的地平线更清楚）。

#### 3.10.3 照片贡献的“纹样”不受遮罩影响

遮罩是纯色，它按比例压缩振幅，但**不改变照片的结构**。0.84 与 0.88 都还留着 16% / 12% 的振幅，足以看出海岸线与碎浪。

#### 3.10.4 两个极性下遮罩的作用方向相反

| | 夜晚 | 白天 |
|---|---|---|
| 文字 | 浅字压深底 | 深字压浅底 |
| 遮罩色 | 往 `--bg-base #0a1223` 拉 | 往 `--bg-base #d3eafd` 拉 |
| 最坏情况 | 最**亮**的底（压不住照片的高光） | 最**暗**的底（暗角把底压过头） |
| 绑定令牌 | `--accent`（1.17:1，最敏感） | `--fg-faint`（最浅的文字）|

> 白天这一侧正是 §3.8.6 那个标定错误的根因：原来的 `--fg-faint` 按“最亮处”算，
> 而真实的约束在“最暗处”。**先把这条修掉，照片才放得进来。**

### 6.11 状态态（吉祥物声部）

五态共用结构：`Q版图` + 一句台词（**出口按钮可选**）。

| 态 | 台词 | 图（专用立绘） |
|---|---|---|
| loading | 「稍等一下哦…我正在努力。」 | Q 版 深呼吸（scale 1→1.012，6s） |
| empty | 「这里还什么都没有…先去别处看看吧」 | Q 版 **摊手**（小手在身侧低位摊开、肩微耸、眉毛一高一低，静止）|
| **404** | 「这里没有东西哦…是不是地址写错了？」 | Q 版 **歪头张望**（手搭额前找东西，静止）|
| error | 「呜…好像出故障了。再试一次可以吗？」 | Q 版 沮丧 |
| easter | 「哼哼，毕竟我是高性能的嘛！」 | Q 版 得意 |

**三态语义必须分清（v0.14 收紧）**：

| 态 | 归因 | 不能用的表情 |
|---|---|---|
| empty | 这一栏**还没内容**（但不是出错）| 沮丧、哭、张望 |
| **404** | **地址写错了**（站是好的）| 哭、沮丧 —— 会让访客以为站点挂了 |
| error | **我出故障了** | 歪头张望 —— 那是在推卸责任 |

> empty 与 404 的台词很像，但归因不同：empty 是「这里空」，404 是「你走错了」。
> 所以：
> · 404 用 **张望**（手搭额前，在找）而不是 **沮丧**（我坏了）
> · empty 用 **摊手**（坦然地承认还没写）而不是 **张望**（那是「找不到」）
>
> 两者的手部动作必须拉开距离，否则 110px 下看起来是同一个表情。

> ⚠️ **别用「剪影 IoU」来判这件事**（试过，不行）。
> 同角色的 Q 版半身像都填满画面，轮廓被**头发 + 猫耳**这块同样的巨大面主导，
> 实测两态 IoU **0.922**（上 / 中 / 下三分区分别 0.939 / 0.941 / 0.895），
> 数看着很像，**眼睛却一眼就能分出**（一个手在额前、一个手在身侧）。
> 有效判据是**按实际显示尺寸（110px）并排看** ——
> `temp/compare_state_silhouette.py` 会输出 110px 与 220px 的并排图 ——
> 再看**内部的脸与手的位置**。我自己列的「< 0.75 才好」是拍的阀值，未标定。

**姿态与表情由立绘本身承担，CSS 不再叠加变形**：

```css
/* ❌ 旧做法：用同一张图假装不同姿态 */
.state--empty .state__art{ transform: rotate(2deg) }   /* 假装「歪头」 */
.state--error .state__art{ opacity: .62 }              /* 把不对的表情压哑 */
```

前者会把绘好的头又拧一次；后者只会显得发灰、像真的坏了。
每一态都应该有自己的图（命名 `ATRI-bot-<态>.png`）。

- 容器用 `--r-mascot`（32px）与 1.5px 描线
- 描线颜色用 `--mascot-line-on-dark`: 夜 `rgba(222,206,194,.30)` / 昼 `rgba(14,53,87,.34)`（深底上不能用 `#010101`）
- 允许背景用 `--mascot-dress` 的 12% 透明度
- `.state__k` 在整页场景下是 **`<h1>`**（给屏幕阅读器一个真标题），
  所以要显式压掉 h1 继承来的字族与字重，保持 mono 小标签的观感
- **禁止**在这些态之外使用这些台词

**整页状态面板 `.page-state`**（404 与空页共用同一版式，只换 `.state--xxx` 与文案）：

```css
.page-state{ padding:168px 0 var(--sec-py); min-height:70vh;
             display:grid; place-items:center;
             --state-art:110px; }   /* 整页比内嵌大一档（88 → 110 = +25%）*/
```

两个子类各管一途：`.state--error`（404）、`.state--empty`（支持 / 联系）。
404 多一行 `.page-state__path` 回显请求的路径，并保留一个「回到首页」按钮
（`<div class="page-state__cta">`）；**empty 两页不放按钮** —— 台词「先去别处看看吧」
已把出口说清楚，再加按钮是重复。`.page-state__cta` 这个类为 404 保留。

**图尺寸是可覆写的**：默认 `88px`，由 `--state-art` 承载。
某一态需要更大时，在它的上下文里覆写即可，不必另写选择器：

```css
.state__art{width:var(--state-art,88px);height:var(--state-art,88px);object-fit:contain}
.page-state{--state-art:110px}      /* 整页状态：放大 25%。该页只有这一张图、文案也短 */
```

> ⚠️ **改了显示尺寸，务必重出素材**。素材按 `显示尺寸 × 2` 备料：
> 88px → 176²、110px → 220²。两边不同步的话，高分屏会拉伸放大。
> `temp/make_state_art.py` 里的 `CSS_SIZE` 就是为此存在的，改一边就要改另一边并重跑。

**专用图与通用图**：404 用 `ATRI-bot-404.png`、empty 用 `ATRI-bot-empty.png`，
两张都是专用立绘；其余三态（loading / error / easter）目前**复用导航的同一个人物图**，

> ⚠️ **别给 `.state--error .state__art` 加透明度来「压哑」表情。**
> 那是在 404 还借用「吐舌坏笑」贴纸图标时的权宜之计 —— 表情与文案相反，只好压暗遮丑。
> 换成对的表情后，再压暗只会显得发灰、像真的坏了。

### 6.13 作品集画廊（少女声部）

三段结构：页头 → 画廊 → 宝箱。整页属**少女声部**（硬边、V 形切角、
**不放 Q 版头像**）—— §2.2 那条「功能卡片里永远不出现 Q 版头像」就是管这个。

```
works-hero        页头   WORKS / 作品 的 mono 小标签 + h1 + 一句说明
works-gallery     画廊   原生横向 scroll-snap，一张一屏居中
works-reward      宝箱   小游戏奖励：播放器 + 下载（默认 hidden）
```

**为什么用 `scroll-snap` 而不是旧版那套 3D 旋转门**

| | 旧：3D 旋转门 | 新：scroll-snap |
|---|---|---|
| 驱动 | `animation` 自动转 | 用户滑动 / 滚轮 / 方向键 |
| 键盘 | ❌ 够不着 | ✅ 原生可聚焦可操作 |
| 触摸 | ❌ | ✅ |
| 减少动效 | ❌ 只能整段关掉 | ✅ 尊重系统设置 |
| 依赖 | jQuery + GSAP 两个 CDN | **0 行 JS 也能翻** |

> ⚠️ 旧版那条 `-webkit-box-reflect` **不是降级，是不显示** ——
> 非标准属性在 Firefox 上整块消失，而作者会以为它一直在。

**居中轮播的写法**：容器两侧各留 `(口宽 − 卡宽)/2` 的 padding，
卡片便落在正中、邻卡自然露边。`scroll-padding-inline` 要与 padding 一致。

> ❗ **别用 `scrollIntoView` 来翻页**。实测：`scroll-padding-inline` 的值是
> 未解析的 `calc(0.5 * (100% - min(720px,100%)))`，浏览器拿不到具体 px，
> 于是以为「这张卡已整张在视口里」而不动；直接赋 `scrollLeft` 又会被
> `mandatory` 吸附搅乱（赋 568 被拉回 0）。**自己算偏移 + `scrollTo` 才可靠**。
> 也不能用 `offsetLeft`：容器没有 `position:relative`，`offsetParent` 是别的祖先。

**控件是增强，不是前提**：`.gallery__bar` 默认 `display:none`，
由 JS 加 `.is-live` 才亮出来（同理才隐藏原生滚动条、才允许压暗邻卡）。
没 JS 时留着原生滚动条可用，不会出现按不动的死按钮、也不会留半透明内容。

**宝箱（小游戏奖励）**

- HTML 上默认 `hidden`，由 `reward.js` 揭示。反过来做（默认可见再隐藏）
  会在每次进页时闪一下，锁定的人也会先瞄到一眼
- `preload="none"` ⇒ 不点播放就**一个字节都不取**（5.4 MB 的文件不该因页面打开就下载）
- 解锁状态存 `localStorage`（键 `atri_works_reward`）。
  **它不跨设备、不跨浏览器，无痕/清缓存就没了；打开 DevTools 写个键值就能解锁。**
  当彩蛋可以，**当权限不行**
- ⚠️ **它挡不住文件本身**。静态站没有鉴权，`assets/audios/` 下的东西
  任何人直接敲 URL 都能拿到。所以这是**体验设计，不是内容保护**
- 调试开关：`?debug=1` 强制显示（也可用于本地开发）、`?debug=0` 强制隐藏。
  代码里的 `DEV_SHOW = true` 为调试期默认显示，**上线前改 `false`**
- 小游戏将来做在画廊与宝箱之间，通关时调 `window.atriWorksReward.unlock()`
- 下载不走裸露的 `<a download>`（原因见下段）

> ⚠️ **CF Pages 不支持 HTTP Range（206）。** 官方文档（Serving Pages → Behavior）：
> *"Pages currently returns 200 responses for HTTP range requests; however,
> the team is working on adding spec-compliant 206 partial responses."*
>
> 也就是说对 Range 请求返 **200 + 全量**，没有 `Content-Range`。
> **本地实测**（响应头确实无 `Accept-Ranges`）：`audio.seekable` 仍报全段
> `[0, 241.4]`，跳到 120 秒成功 —— 但那一次已缓冲到 225 秒，**没测到「跳到未缓冲处」**。
> 用 CDP 限速想复现慢网，限速没作用到媒体请求，**实验无效**。
>
> 所以：**「慢网下拖不动进度条」是推断，不是实测结论**，别当已证实的事写。
> 合理推断是 —— 没有 partial response，跳到未缓冲位置就得从头重下；
> 对 5.37 MB 的文件，正常宽带下很快缓冲完，影响有限。
> 宝箱里的「下载」链接作为兜底保留。

**下载：不用裸露的 `<a download>`，改走 `fetch` → Blob → object URL**

`download` 属性**只对同源资源生效**；不同源时浏览器会**静默忽略**它，
直接导航过去 —— 访客看到的是一个音频播放界面，而不是「已保存」。
而「同源」这件事不由页面控制：反向代理、内嵌 WebView、
带域名重写的预览环境都可能把 `assets/audios/…mp3` 变成跳源。

所以 `reward.js` 拦住点击，自己取回、自己保存：

| 步骤 | 作用 |
|---|---|
| `fetch(href)` + `res.body.getReader()` 流式读取 | 边下边报进度（5.4 MB 在慢网上要等一会儿） |
| `new Blob(parts, {type:'audio/mpeg'})` | 封成内存对象 |
| `URL.createObjectURL(blob)` | **`blob:` URL 恒与页面同源** ⇒ `download` 一定生效 |
| 临时 `<a download="宝箱の毎日.mp3">` 后 `.click()` | 触发保存，文件名由我们指定 |
| 按钮文字 `下载中 n% → 已开始下载 → 下载` | 有反馈；连点会被 `aria-busy` 拦掉 |

> ⚠️ **`URL.revokeObjectURL` 不能紧接着调** —— 部分浏览器还没读完就被掉断。
> 留 10 秒（5.4 MB 的 blob，多留一会儿不碍事）。
>
> ⚠️ **原生的 `<a href download>` 必须留在 HTML 里**：没 JS 时它是唯一通路，
> 有 JS 时它是 `.catch()` 之后的退路。渐进增强，不是二选一。
>
> ❗本环境**量不到「是否真的存了盘」**：这个内嵌浏览器不向 Playwright
> 上报 download 事件 —— 而改动**之前**的原生链接也一样不上报。
> 能验证的是代码路径：`createObjectURL` 被调到、`blobSize` 等于
> 响应的 `content-length`、以及那个带 `download` 的 blob 链接确实被点了一下。

### 6.14 文档分区（少女声部）

主导航新增「文档」，位置在 **首页 与 作品集 之间**。四个页面：

```
docs.html            概览        这是什么、能做什么、贡献与许可
docs-start.html      快速开始    NapCat / 数据库 / 模型 / 启动 / Docker
docs-structure.html  项目结构    目录树
docs-arch.html       架构设计    消息流 / LLM 流程 / 记忆系统
```

内容以仓库 README 为准，**不使用任何 emoji**。

**两栏版式**：侧边栏（左，粘滞）+ 正文（右）。

```css
.docs__layout{
  display:grid; grid-template-columns:216px minmax(0,1fr);
  gap:var(--space-8); padding-inline:var(--gutter);
  align-items:start;          /* 别让侧边栏被拉高到和正文一样长 */
}
.docs__article{max-width:46em}
```

> ⚠️ **限宽加在 `.docs__article`，不是 `.doc-body`。**
> h2 的上边框、lede 的下边框都挂在 article 这一层；
> 只限 `.doc-body` 的话，那两条横线会拉满整个宽栏，看着像排版漏了。

**侧边栏两段**：上半是**四个页面**，下半是**本页**的章节锚点。

> ⚠️ 「本页」只渲染**当前页**自己的章节。把四页的锚点全列出来会指向别页不存在的 id，
> 全是死链 —— 点了没反应，而且不报错，很难发现。生成器里有一条自检盯着它。

窄屏（< 900px）塌成一栏：侧边栏不再粘滞，页面链接排成一行可横滑，
**「本页」锚点整块隐藏** —— 那是七八个链接的纵向块，会在正文之前先堆掉一整屏。

**全宽与 `--gutter`**：导航栏与文档侧边栏都要**贴屏幕最左边**（用户要求），
所以两者都不能受 `--maxw` 居中约束，共用一个 `--gutter:clamp(20px,2.6vw,48px)` 保证左缘对齐。

> ⚠️ `.docs__layout` **不能挂 `.wrap`** —— `.wrap` 的 `max-width` 会把整块拉回居中，
> 侧边栏就跟着退到屏幕中间去了。

**顶部留白比落地页窄**（用户反馈「上方的空白区域有点大」）。

| 断点 | `.docs` 上内边距 | 导航高 | 净空 |
|---|---|---|---|
| > 899px | **120px** | 72px | 48px |
| ≤ 899px | **110px** | 66–81px | 29–44px |

> ⚠️ **别照抄 `.hero` / `.works` / `.page-state` 的 168px。**
> 那三页是落地页，宽裕的留白是故意的；文档是查阅型页面，正文该尽快进入视野。
> 原来统一用 168px，导航只占 72px ⇒ 中间空了 96px，整块看着像「没加载完」。
>
> 侧边栏粘滞偏移 `top:104px` 与正文 `h2{scroll-margin-top:104px}` 都不受此改动影响 ——
> 它们只跟导航高度（72px）有关，都留了 32px 的间隙。

**文档内部换页：无离场 + 只淡正文；跨栏目才整页平移**（用户两轮要求后的最终形态）。

用户原话：
> 「文档内部页面的切换不是右上角那一行按键点击后不同页面的切换，所以不需要这个翻页的感觉」

| 跳转 | 方向 | 离场 | 主容器 | 侧边栏 | 正文 | 时长 |
|---|---|---|---|---|---|---|
| docs ↔ docs-* | `fade` | **无（直接跳）** | 不动 | 不动 | `navFadeIn` / `vtFadeIn` | **300ms** |
| index → docs | `forward` | `navPushOutLeft` | `navPushInRight` | — | — | 240 / 420ms |
| works → docs | `back` | `navPushOutRight` | `navPushInLeft` | — | — | 240 / 420ms |

四条设计约束，**缺一条就会退化成翻页感**：

1. **到达**：两边 slug 都以 `docs` 开头 ⇒ `dir='fade'`（`assets/js/transition.js`）。
2. **离场什么都不做**：点击处理器里文档内部链接**直接 `return`** ——
   不 `preventDefault`、不写 `data-nav-out`、不推迟跳转。
   > ❗两段式回退的「整页淡出 → 跳 → 淡入」中间会闪一下，那正是要消掉的翻页感；
   > 而按 `ORDER` 算出来的 `forward` 左推更明显。
   > 一开始只改了到达、没改离场，结果离场仍是 `navPushOutLeft`，用户立刻就看出还是翻页。
3. **淡化只作用于 `.docs__article`** —— 不是 `.docs`、更不是 `:root`。
   侧边栏两页完全一样，是视觉锚点；淡它整块儿就像换了页。
4. **VT 路径用命名组**：`.docs__article{view-transition-name:doc-article}`（无条件挂），
   `html[data-vt="fade"]::view-transition-old/new(doc-article)` 走 `vtFadeOut` / `vtFadeIn`，
   而 `root` 那一路**不带任何动画**。

```css
/* 跨栏目的整页平移：动画名与时长都走变量，两套共用一条规则 */
::view-transition-old(root){
  animation:var(--vt-out,none) var(--nav-dur,var(--dur-nav-vt)) var(--ease-sea) both;
}
::view-transition-new(root){
  animation:var(--vt-in,none) var(--nav-dur,var(--dur-nav-vt)) var(--ease-sea) both;
}
html[data-vt="forward"]{ --vt-out:vtSlideOutLeft;  --vt-in:vtSlideInRight }
html[data-vt="back"]   { --vt-out:vtSlideOutRight; --vt-in:vtSlideInLeft  }

/* 文档内部：root 不动，只有命名组里的正文淡化 */
.docs__article{ view-transition-name:doc-article }
::view-transition-group(doc-article){ animation-duration:var(--nav-dur) }
html[data-vt="fade"]::view-transition-old(doc-article){ animation:vtFadeOut var(--dur-nav-fade) var(--ease-sea) both }
html[data-vt="fade"]::view-transition-new(doc-article){ animation:vtFadeIn  var(--dur-nav-fade) var(--ease-sea) both }
```

回退路径（`@view-transition` 不可用时）同理，只是写在元素上：

```css
html[data-nav-in="fade"] .docs__article{ animation:navFadeIn var(--dur-nav-fade) var(--ease-sea) both }
```

> ❗**不要把 `fade` 挂在 root 上**（早期版本是 `html[data-vt="fade"]{--vt-out:vtFadeOut}`）。
> 那会整页淡，侧边栏跟着一起淡，和上面第 3 条矛盾 —— 而回退路径已经只淡正文了，
> 两条路行为对不上。
>
> 淡化用 300ms 而不是 520ms：那么长的淡化会让文字看起来糊一下。

实测六组（`emulateMedia({reducedMotion:'no-preference'})` + 清缓存）：

| 跳转 | `data-vt` | 主容器 | 侧边栏 | 正文 |
|---|---|---|---|---|
| index → docs | forward | `navPushInRight` | — | — |
| docs-arch → works | forward | (works) `navPushInRight` | — | — |
| works → docs | back | `navPushInLeft` | — | — |
| docs → docs-start | **fade** | **none** | **none** | **`navFadeIn`** |
| docs-start → docs-arch | **fade** | none | none | **`navFadeIn`** |
| docs-arch → docs（回头） | **fade** | none | none | **`navFadeIn`** |

离场侧实测：文档内部 `{out: [], prevented: false}`；跨栏目 `{out:["data-nav-out=forward"], prevented:true}`。

> ⚠️ **量「到达瞬间」的动画不能靠 `waitForNavigation`，也不能在一次 `evaluate` 里轮询 URL** ——
> 导航会销毁执行上下文，两种写法都会炸（Timeout / `Execution context was destroyed`）。
> 用 CDP `Page.addScriptToEvaluateOnNewDocument` 注入采样器，让**到达页自己**在
> `DOMContentLoaded` 时把结果写进 `window.__arrival`，点完后等 2200ms 再读。

**内容由生成器产出，不手写四个 HTML**（`temp/build_docs.py` + `temp/docs_content.py`）。
四页的外壳完全一样，手抄四份必然有一天改了三份忘一份。

> ⚠️ **改内容改脚本，不要直接改 `web/docs*.html`** —— 重跑会被覆盖。
> 改样式去 `assets/css/layout.css`，那里不会被覆盖。

## 8. 招牌交互

### 8.1 水面倒影导航（全站标志）

**结构**

```html
<a class="nav__link" href="#features">
  <span class="nav__label">功能</span>
  <span class="nav__mirror" aria-hidden="true">功能</span>
</a>
```

**实现**
```css
.nav__link{ position:relative; color:var(--fg-muted); }
.nav__mirror{
  position:absolute; left:0; right:0; top:100%;
  transform:scaleY(-1);
  opacity:.20; filter:blur(1.4px);
  pointer-events:none;
  -webkit-mask-image:linear-gradient(to bottom,transparent 25%,rgba(0,0,0,.85) 100%);
          mask-image:linear-gradient(to bottom,transparent 25%,rgba(0,0,0,.85) 100%);
}
```

> 注意 mask 方向：元素被 `scaleY(-1)` 翻转后，其**局部底部**在视觉上位于**上方**（贴近文字），所以 mask 要让局部底部不透明 —— 即 `to bottom` 从透明到不透明。

**三态**

| 态 | 倒影 | 文字 | 下划线 |
|---|---|---|---|
| rest | `opacity .20`，无位移 | `--fg-muted` | `scaleX(0)`，隐形 |
| hover | `opacity .42`，2.4s 循环水纹（`translateX ±1.5px` + `skewX ±0.6deg`） | `--fg` | **`--accent`（青蓝）**，`scaleX(0→1)` 从左端展开 |
| active | `opacity .55` | `--accent-warm` | **`--accent-warm`（暖色）**，常驻 `scaleX(1)` |

```css
.nav__link::after{
  content:"";position:absolute;left:12px;right:12px;bottom:4px;height:1px;
  background:var(--accent);
  transform:scaleX(0);transform-origin:left center;
  transition:transform var(--dur-2) var(--ease-sea),
             background var(--dur-2) var(--ease-sea);
}
.nav__link:hover::after      {transform:scaleX(1)}                          /* 青蓝，未选中 */
.nav__link.is-active::after  {transform:scaleX(1);background:var(--accent-warm)}  /* 暖色，当前页 */
```

**这条线的颜色是有语义的，不是随手挑的**：
青蓝表示"这条你可以去"，暖色表示"你就站在这儿"。
所以切换页面时线不会消失再重画 —— 它**原地换色**，位置也留在原处。

两个实现细节：
- 用 `transform:scaleX` 而不是 `width` —— 后者每帧都要重排
- `transform-origin:left center` 让它**从左侧长出来**，而不是从中间往两头撑

**尚未实现**（demo 里也没有，属第二期）：active 的海平线火花点 + `--glow-warm`，以及把下划线换成 V 形折线。
移动端导航改为横向滚动 tab 时，下划线落到贴边处并加粗成 2px 指示条：
```css
@media (max-width:639px){ .nav__link::after{left:10px;right:10px;bottom:0;height:2px} }
```

**海平线**：导航容器底部 `1px solid var(--line-color)`，为倒影提供"水面"。**没有这条线，倒影就失去物理依据。**

**可访问性**：倒影 `aria-hidden="true"`（避免读屏重复）；`:focus-visible` 用 `outline:1px dashed rgba(251,228,207,.7); outline-offset:6px`（不用圆角 outline）。

### 8.2 暖光呼吸

```css
@keyframes emberBreath{

  50%    { opacity:1;   transform:scale(1.045); }

/* 周期 4.5~6s，用于首屏火花光斑与导航 active 火花点 */
```

### 8.3 区块转场（替代旧版立方体）

滚动进入视口时：
1. 内容 `translateY(18px) → 0`
2. `opacity 0 → 1`
3. **倒影同步延迟 60ms**，产生"水面慢半拍"的错觉
4. `IntersectionObserver`，`threshold: 0.16`，仅触发一次

曲线统一 `--ease-sea`，时长 `--dur-3`。

### 8.4 待机动效清单

| 元素 | 动效 | 周期 | 幅度 |
|---|---|---|---|
| 波浪（背景层） | 横向位移 | ≥ 16s | 0.6% ~ 1.2% |
| 火花光斑 | 呼吸 | 4.5~6s | opacity ±18% |
| 吉祥物挂件 | 呼吸 | 6s | scale 1→1.012 |
| 立绘 | 上下漂浮 | ≥ 20s | ±6px |
| 星点 | 亮度 | ≥ 24s | opacity ±10% |

**验收标准：盯着看 5 秒，先注意到的是"内容"，而不是"动画在动"。**

### 8.6 跨页平移转场

四个页面之间切换时，旧页连续滑出的**同时**新页从另一侧滑入，方向跟随导航顺序。

**方向规则**：只由「从哪一页到哪一页」决定 —— 首页 → 作品集 → 支持 → 联系 为 `forward`（整页向左推），
反向为 `back`。**与是谁发起的跳转无关**，所以浏览器的前进 / 后退按钮也能拿到正确方向，不需要额外记账。

```js
var ORDER = ['index','works','support','contact'];   /* 不带扩展名的 slug，原因见下 */
var a = ORDER.indexOf(from), b = ORDER.indexOf(here);
if (a > -1 && b > -1) dir = b > a ? 'forward' : 'back';   /* from 取自 sessionStorage */
```

> ⚠️ **必须用不带扩展名的 slug，不能用文件名。**
> Cloudflare Pages / GitHub Pages 会把 `/works.html` **重定向**成 `/works`，
> 于是落地页的 `pathname` 就没有 `.html` 了。若按文件名比对，`indexOf` 返回 `-1`，
> 方向算不出来，**转场在真实托管上静默失效** —— 而本地用 `python -m http.server` 测却一切正常
> （它不做这个重定向）。这个坑实测踩过一次。

#### 8.6.1 主路径：跨文档 View Transitions

默认走这条路。浏览器自己拍下旧页快照，于是**旧页滑出与新页滑入是并行的**，
是一次连续运动，中途不存在断点。

```css
@view-transition{navigation:auto}

html[data-vt="forward"]{ --vt-out:vtSlideOutLeft;  --vt-in:vtSlideInRight }
html[data-vt="back"]   { --vt-out:vtSlideOutRight; --vt-in:vtSlideInLeft  }

@keyframes vtSlideOutLeft { to{transform:translateX(-100%)} }
@keyframes vtSlideInRight { from{transform:translateX(100%)} }

::view-transition-image-pair(root){ isolation:auto }
::view-transition-group(root){
  animation-duration:var(--dur-nav-vt); animation-timing-function:var(--ease-sea);
}
::view-transition-old(root){ animation:var(--vt-out,none) var(--dur-nav-vt) var(--ease-sea) both; mix-blend-mode:normal }
::view-transition-new(root){ animation:var(--vt-in, none) var(--dur-nav-vt) var(--ease-sea) both; mix-blend-mode:normal }
```

| 令牌 | 值 | 说明 |
|---|---|---|
| `--dur-nav-vt` | `520ms` | 整程时长。old/new **并行**，所以这一个值就是全部 |

**四个必须做对的地方**

1. **方向用 CSS 变量传，不要用带祖先的选择器。**
   `html[data-vt="forward"]::view-transition-old(root)` 这种写法要赌
   `::view-transition-old` 算不算 `html` 的后代 —— 伪元素树里它是 `::view-transition` 的孙辈，
   两种解析口径的实现都存在。自定义属性沿伪元素树继承，写 `var(--vt-out)` 就完全绕开了这个问题。
2. **必须清掉默认的交叉淡化**（`animation` 里的 `none` 兜底 + `mix-blend-mode:normal`）。
   淡化会把「平移」的实感冲掉 —— 这正是它原来观感不连贯的原因之一。
   `::view-transition-image-pair` 默认 `isolation:isolate`，是为交叉淡化准备的；
   两层相邻滑动时接缝会按 `plus-lighter` 混合、发白，要一并解掉。
3. **`::view-transition-group(root)` 的时长要跟 old/new 对齐。**
   UA 给 group 的几何动画默认 250ms。若两页的视口宽度不同（例如其中一页内容够长、
   出现了纵向滚动条），它会把快照横向缩放一下，时长不一致就会在中途「抖」一下。
4. **`@view-transition` 必须写在两个页面的 CSS 里**，只有一边开启不会触发。
   `prefers-reduced-motion` 下改成 `navigation:none` 直接关掉 ——
   压到 `0.01ms` 仍会拍快照、建伪元素，只是白跑一趟。

#### 8.6.2 回退路径：JS 两段式推入

Chromium 126+ / Safari 18.2+ 走主路径。不支持的（如 Firefox）由 `transition.js`
照常播原来的两段式：离场 240ms → 导航 → 入场 420ms。

**离场**：捕获阶段拦下站内链接，先播 240ms 推出去，再交给浏览器跳。
`sessionStorage` 被禁用（隐私模式）时静默降级 —— 只是没有入场动画，页面照常。

```css
@keyframes navPushOutLeft { to{ transform:translateX(calc(-1 * var(--shift-nav))); opacity:0 } }
@keyframes navPushInRight  { from{ transform:translateX(var(--shift-nav)); opacity:0 } }
html[data-nav-in="forward"]            :is(.hero,.page-pending,.site-footer){ animation:navPushInRight var(--dur-nav-in) var(--ease-sea) both }
html.is-leaving[data-nav-out="forward"] :is(.hero,.page-pending,.site-footer){ animation:navPushOutLeft var(--dur-nav-out) var(--ease-sea) both }
```

| 令牌 | 值 | 说明 |
|---|---|---|
| `--dur-nav-out` | `240ms` | 推出去，比推入快 —— 离开不该让人等 |
| `--dur-nav-in` | `420ms` | 推入 |
| `--shift-nav` | `clamp(40px,9vw,150px)` | 位移量。**只有回退路径用得到** |

**四条约束（只对回退路径成立）**

1. **只推内容，不推背景。** 海面 / 星点 / 遮罩 / 导航都是 `fixed`。一旦被 `transform` 的祖先接住，
   `fixed` 就会改成相对该祖先定位，整块背景会跟着飞走。
2. **导航故意不动。** 它在四页上完全一致，钉住反而让内容像在它下面滑动 —— 像换水，不像换页。
3. **入场方向必须在首帧之前写到 `<html>` 上**（所以 `transition.js` 在 `<head>` 里同步执行），
   否则会先看见内容停在原位、再“跳”去右边，闪一帧。
4. **动画跑完要摘掉标记。** `data-nav-in` 带着 `will-change:transform,opacity`，
   一直挂着会平白多一个合成层。`DOMContentLoaded` + `--dur-nav-in + 380ms` 后 `removeAttribute`。

**bfcache**：页面可能在“已经推出去”的状态下被冻结。`pageshow` 且 `ev.persisted` 时必须把
`is-leaving` / `data-nav-out` / `data-nav-in` / `data-vt` 全部清干净，
否则一按后退就是一片空白 —— 内容全在屏幕外。

#### 8.6.3 两条路径如何共存

两个标记**同时写**，各管一路；转场若在跑，CSS 里这一条把回退动画关掉，所以不会双播：

```css
html:active-view-transition :is(.hero,.page-pending,.site-footer){ animation:none !important }
```

**为什么不用 `pageswap` / `pagereveal` 事件判断**（踩过的坑）

- 实测在 VS Code 内置浏览器（Electron 42 / Chrome 148）里，这两个事件**一个都不触发**，
  连 `pageswap` 都不发 —— 尽管 `PageRevealEvent` 这个接口是存在的。
  所以「接口存在」不等于「事件会来」，依赖它会静默失效。
- **方向本来就能同步算出来**：上一页存在 `sessionStorage`、本页 `pathname` 就在手边，
  完全不需要等事件。

**「这次到底会不会跑转场」怎么判断**：点击那一刻没有同步 API 可问。所以用**上一次导航的实测结果**
推断，存在 `sessionStorage`：

| 值 | 含义 | 行为 |
|---|---|---|
| `'1'` | 上次确实跑成了转场 | 放行，不播离场动画（否则旧页快照会带上偏移） |
| `'0'` | 上次没跑成 | 照常播离场动画 |
| 空 | 还没试过 | 先乐观放行 —— 宁可第一次少一段离场动画，也不能冒险毁掉旧页快照 |

判断依据是**本页 head 脚本执行时 `document.activeViewTransition` 是否非空** ——
这是唯一能确认「转场真的跑了」的同步信号。一次导航后就能自我纠正。

**怎样验证它真的在跑**（这条很有用，因为肉眼看不出用的是哪条路径）：

```js
for (const a of document.getAnimations()) {
  const pe = a.effect && a.effect.pseudoElement;      // "::view-transition-old(root)"
  if (pe && String(pe).includes('view-transition')) {
    console.log(pe, a.animationName, a.effect.getTiming().duration);
  }
}
```

主路径应该看到 `vtSlideOutLeft` / `vtSlideInRight`（各 520ms）；
若拿到空数组，说明走的是回退路径。
⚠️ **不要用 `requestAnimationFrame` 采样** —— 后台标签页里 rAF 被暂停，会采到空结果。

`prefers-reduced-motion` 时两条路径都关闭，直接跳转。

## 11. 可访问性

- 正文对比度 ≥ **4.5:1**：`--fg`（暖白）on `--sea-900 #0a1223` ≈ **17.6:1** ✓
- **实测结果（v0.5）**：

  | 配对 | 比值 | 结论 |
  |---|---|---|
  | `--fg #fcfaf3` on `--sea-800 #142f5c` | 12.6:1 | ✅ 充足余量 |
  | `--fg` on `--sea-700 #223a68` | 10.7:1 | ✅ |
  | `--fg` on `--sea-500 #2664ab` | 5.3:1 | ✅ 但这是最后一道底线，不可再亮 |
  | `--accent #397f9d`（旧） on `--sea-800` | **2.95:1** | ❌ 已修复为 `#70b5d5` |

- **`--accent` 属正文级**：它承担序号、标签、命令、链接的文字色，必须 ≥4.5:1。v0.4 之前的值不达标，已在 §3.1 修正
- `--fg-faint` **仅用于装饰性文字**（页码、水印），不得承载信息
- **不可承载文字的表面**：`--sea-500 #2664ab`。任何强调色在它上面都无法达到 4.5:1（最优的 `#89cff0` 仅 3.51）
- 所有交互元素必须有 `:focus-visible`，样式统一为 1px 虚线暖白框 + 6px offset
- 装饰元素（倒影、波浪、星点、光斑）一律 `aria-hidden="true"` 或 `pointer-events: none`
- SVG 图标使用 `stroke-linecap: butt`（硬边，呼应少女声部），并带 `aria-hidden="true"`，语义由相邻文字承担
- 不使用 `outline: none`，不使用 `tabindex="-1"` 逃逸键盘顺序
- 语言标注：`<html lang="zh-CN">`，日文段落加 `<span lang="ja">`
- 尊重 `prefers-reduced-motion: reduce`
- 两套主题（昼 / 夜）**都已存在**。默认按访客本地时间取初值（06:30–18:00 判为白天），**并提供手动切换**（§3.9）。**不跟随 `prefers-color-scheme`** —— 跟随的是时间
- 因为存在两套主题，**组件必须只用语义层令牌**（§3.1），不得直接引用 `--sea-*` 等原始色阶，否则切换主题时会残留夜色
- **切换瞬间不能让文字裸露**：极性是**阶跃**的（不插值）。两套静态色值之间不存在死区，
  但过渡期间仍要靠 §3.9.2 的整页盖布遮住交接 —— 不能在浅色文字底下推一块中间调
- **裸坐在环境底上的文字仍要逐页校验**：本期虽无遮罩（§3.8 不实现），但两套静态底色的对比度下限仍然适用。
  改任何色值前先跑一遍 `temp/verify_dawn.py`（它同时校验两套静态色值）
- **`--fg-faint` 不得承载信息**：它的下限是按环境极值定的（夜 5.40 / 昼 5.28），踩在 `--panel--hero` 那类更亮的渐变面板上还会变差。十六进制、坐标、标签一律用 `--fg-muted`

> （`components.css`）。`.state` 是 §6.11 各态**共用**的容器，

### 13.1 托管约束（Cloudflare Pages）

| 项 | 限制 | 本站现状 |
|---|---|---|
| 文件数 | Free **20,000** / 付费 100,000 | 24 个，宽裕 |
| 单文件大小 | **25 MiB** | 最大 4.2 MB（`ATRI-bot-nightsea.png`） |
| 静态资源请求 | **免费且不限量**（官方：requests to static assets are free and unlimited） | — |
| 带宽 | 不限量 | — |
| 部署 | Git 集成（build 留空、输出目录填 `web`）或 `npx wrangler pages deploy web` | — |

**两条会咬人的默认行为（都已踩过）**

1. **`.html` 会被重定向到无扩展名**：`/works.html` → `/works`。落地页 `location.pathname` 没有 `.html`，
   而**本地 `python -m http.server` 不做这个重定向** —— 所以这类问题只在部署后才暴露。
   影响过 §8.6 的转场方向判定。
2. **没有顶层 `404.html` 时，CF 把全站当 SPA**，未匹配路径一律回落到 `/`（200 而非 404），
   网址打错会静默显示首页。⇒ **已放 `web/404.html`**（§9.4 的 error 文案），CF 会对未匹配路径真的返回 404。
   > 注意：`_redirects` **不能**产出 404 状态码（官方文档「Rewrites (other status codes) ❌」），
   > 所以只能靠一个真实的静态 `404.html`，不能靠重写规则。

**目录划分（已落地）**：可上线的东西全部在 `web/` 里，共 **16 个文件 / 0.62 MiB**；
参考素材、本规范、演示页、旧版页面全部在仓库根的 `design/`（13 个文件 / 13.4 MiB）。
两者物理隔开，**不需要额外维护排除清单** —— 部署目标就是 `web/` 本身，
`/design/视觉设计规范.md` 这类地址在线上根本不存在。

**不要自己配缓存** —— CF 已自动给 gzip/brotli、`Etag`、Tiered Cache；额外加 Cache Rule 容易 304 到陈旧资源。

### 13.2 音频（原创，无版权顾虑）

静态托管放音频**完全可行且免费**，但有两条硬约束：

1. **浏览器禁止自动播放带声音的音频**，必须有用户手势才能 `play()`。
   ⇒ 不能做「进页面就响起 BGM」。标准做法是给一个播放按钮，或监听首次任意 `click` 再启动。
2. **必须写 `preload="none"` 或 `"metadata"`**，否则每个访客都会在首屏把整首歌拉一遍。

| 项 | 建议 |
|---|---|
| 格式 | MP3/AAC 兼容面最广；Opus 体积约小一半，但老 Safari 有风险。**MP3 主 + Opus 备** |
| 位置 | `web/assets/audio/`（与 `img` 同级） |
| 体积 | 计入首屏预算的话，BGM 应 ≤ 1.5 MB（128kbps 约 1 分钟） |

### 13.3 小游戏（纯前端，2D，4399 风格）

**可行，不需要任何服务端**：Canvas 2D / Web Audio / Pointer Events 都能用，存档用 `localStorage`。

- **定位是 4399 那种休闲小游戏** —— 不做 3D。这很重要：仓库里 `atri-3d/atri.glb` 是 **30.25 MiB**，
  **超过 CF 单文件 25 MiB 上限**，直接上线会被拒（要过得 Draco/meshopt 压缩几何 + KTX2 压贴图）
- 纯 2D 的话整套资源通常只有几百 KB，与文件数、体积额度都毫无压力
- 页面侧建议：独立页（如 `web/game.html`）+ 自己一个 `<canvas>`，**不要把游戏逻辑塞进主站 JS**
- ❗**一旦要排行榜 / 多人对战 / 云端存档就不行了** —— 那需要 Workers + KV/D1，而静态站调不到
- 触控目标仍需 ≥ 44×44px（§7），键盘操作要同时做，移动端没有键盘
